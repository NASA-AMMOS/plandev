# Workspace versioning scale results: 2026-10-09

First baseline from the scale harness ([README](README.md)) against the `prototype/git-authoritative-revisions`
backend (adapter `GitRevisionsPrototypeDriver`). This is measurement only: no production code was changed or optimized.
Results are in [`2026-10-09/`](2026-10-09/). Each JSON file has, for every operation, its count, median, p95, p99,
min, max and failures, per checkpoint, plus storage diagnostics and correctness checks. Raw per-sample timings were
kept locally but are not checked in.

| | |
| --- | --- |

| Machine | Apple M4 Max, 16 cores, 48 GB RAM, macOS 26.6.2 |
| Filesystem | APFS, internal SSD |
| JVM | Temurin 21.0.9, `-Xmx3g` |
| JGit | 6.10.0.202406032230-r |
| Revision catalog | Postgres 16.14 in Docker (scratch database from the production DDL) |
| `gitDirty` | true only because of an unrelated, pre-existing `sequencing-server/package-lock.json` change |

Caveats:

- One laptop.
- Postgres runs in a Docker VM, so catalog calls include port-forwarding latency.
- "Restart" is in-process: services are rebuilt and JGit caches cleared, but the JIT and the OS page cache stay warm.
- Disk sizes are apparent file sizes.
- The machine was under heavy memory pressure from other work (about 25-33 GB of swap in use).
- The machine idle-slept twice during the first scale attempt. The harness clock pauses with the process, so latencies
  are unaffected; later runs used `caffeinate`.

## Summary

Every scenario finished with every correctness check passing, about 1,500 checks in all:

- every file's bytes, and deleted files staying deleted;
- revision lists and revision counts;
- historical revision content and restore;
- stale-token saves and restores refused;
- If-Match history chains under concurrency;
- state preserved across restart, rebuild, clone, sync and manual packing.

Nothing was corrupted, and nothing failed to reopen or rebuild.

Performance:

1. **Every mutation costs time proportional to the whole working tree**, both its file count and its bytes, regardless
   of what changed. This is the dominant cost at realistic sizes. History depth is not.
2. **Revision creation and rebuild are linear in the number of revision tags in the workspace.** Building N revisions
   is therefore O(N²) in total. The Postgres projection itself is cheap.
3. **The first last-edit lookup after a restart walks the whole history.** It took 12 s at 50k saves.
4. **Storage grows on every save and is never packed**, except incidentally (see the remote section). Text packs
   extremely well; incompressible binary does not pack at all.
5. **Concurrency is correct.** One workspace serializes to about 120-155 saves/s; independent workspaces plateau at
   about 300-330 saves/s in aggregate.

| Operation | Scales with | Measured |
| --- | --- | --- |
| Save / restore / move / delete | files + bytes in the workspace | ~0.11 ms per file + ~50 ms per MiB, every mutation |
| `revision.create`, rebuild | revision tags in the workspace | ~0.23-0.32 ms per tag |
| Revision list, state matches no revision | that file's revision count | ~0.1 ms per revision |
| Revision list, state matches latest; preview; read | nothing measurable | 0.1-5 ms everywhere |
| First last-edit lookup after restart | history (commits × paths changed) | 150 ms at 1k saves, 12 s at 50k |
| Publish, clone, incremental sync | history size | at 10k saves: 7.7 s, 1.8 s, 1.6 s |
| Disk | saves × change size; packing only helps text | ~4 KB per small save, loose; binary = full size per save |

## 1. Working-tree size (`tree-size`)

Files arrive in a single import, then the standard probe runs. "+ N MiB" means 100 small files plus N 1 MiB text files
that are never touched. Medians in ms; each probed operation ran 5 times.

| Workspace | save existing | save new | restore | `revision.create` | rebuild | list (no match) | read | first `lastEdit` after restart |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 100 files | 22.7 | 23.5 | 19.0 | 10.2 | 9.1 | 2.1 | 0.2 | 5.9 |
| 1,000 files | 91.9 | 93.9 | 91.1 | 15.9 | 14.7 | 1.9 | 0.2 | 6.4 |
| 10,000 files | 1,074 | 1,068 | 1,034 | 87.3 | 89.1 | 1.5 | 0.1 | 13.6 |
| 50,000 files | 5,527 | 5,468 | 5,420 | 412 | 377 | 1.7 | 0.1 | 42.9 |
| 100 files + 8 MiB | 410 | 414 | 409 | 7.5 | 7.2 | 1.6 | 0.1 | 4.3 |
| 100 files + 32 MiB | 1,635 | 1,581 | 1,552 | 8.7 | 6.0 | 1.5 | 0.1 | 4.0 |
| 100 files + 128 MiB | 6,557 | 6,324 | 6,206 | 9.3 | 10.3 | 1.1 | 0.1 | 4.7 |
| 100 files + 512 MiB | 25,307 | 25,830 | 27,535 | 16.9 | 12.7 | 2.1 | 0.3 | 5.4 |

Import time: 0.3 s for 100 files, 0.65 s for 1k, 6.6 s for 10k, 33.6 s for 50k, and 27 s for the 512 MiB case.

Every mutation (save, new file, restore) is linear in file count (~0.11 ms per file) and in total content bytes
(~50 ms per MiB), even when nothing else changed. The likely cause is the whole-tree Git passes around each mutation:
the trust check, `add .`, `add -u`, status, and the clean check. At least one of them appears to re-hash large files'
content. That is a hypothesis to confirm with a profiler; this branch does not fix it.

Revision creation depends on file count only weakly (~0.008 ms per file). Reads, previews and lists don't depend on
tree size at all.

The same effect shows in the year mix. In a quick-profile attribution run with the same seed, about 5 medium and binary
files in a 200-file workspace raised the median save from 41 ms (`year.mediumShare=0 year.binaryShare=0`) to 256 ms
(the default mix).

## 2. History depth (`history-depth`)

50 small files plus one hot file with revisions; saves go round-robin; the probe runs at each depth.

| Saves | save existing | `revision.create` | list (no match) | restore | rebuild | `.git` MB | loose objects |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 16.2 | 8.9 | 2.1 | 20.0 | 12.3 | 0.2 | 300 |
| 1,000 | 15.9 | 9.6 | 3.0 | 15.3 | 11.9 | 4.3 | 3,458 |
| 5,000 | 15.9 | 12.1 | 3.2 | 16.2 | 14.3 | 20.1 | 15,540 |
| 10,000 | 16.1 | 13.3 | 4.0 | 18.8 | 15.8 | 39.8 | 30,618 |
| 25,000 | 19.1 | 15.6 | 5.2 | 20.4 | 17.6 | 98.8 | 75,700 |
| 50,000 | 25.4 | 22.1 | 7.8 | 26.7 | 20.4 | 197.0 | 150,782 |

Across all 50,005 build saves, the median rose only from 16.7 ms to 18.3 ms (the JSON has a 20-bucket series). The
slowest single save took 7.2 s, an isolated stall.

After a restart at 50k saves, the **first last-edit lookup took 11,958 ms**; every call after that took 0.5 ms. Any
first request that needs history-derived metadata pays this after every restart, and the cost grows linearly with
history. Other first operations after a restart were not noticeably cold.

Storage: about 4 KB per save, all of it loose (about 3 loose objects per save). Nothing ever packs them.

## 3. Revisions (`revisions-one-file`, `revisions-spread`)

Each step is a save plus a revision. "Spread" uses 1,000 files, round-robin.

| Revisions | one file: create | one file: list (no match) | one file: rebuild | spread: create | spread: rebuild |
| --- | --- | --- | --- | --- | --- |
| 100 | 27.7 | 8.7 | 32.5 | 47.1 | 50.6 |
| 1,000 | 234 | 97.4 | 239 | 325 | 339 |
| 2,000 | 455 | 195 | 487 | 644 | 666 |

- **Create and rebuild:** linear in the total revision tags in the workspace, not per file. That is about 0.23 ms per
  tag on one file and 0.32 ms per tag spread. Creation reads and validates every revision tag to find the next ordinal
  and the latest state.
- **Building many revisions is quadratic.** 2,000 revisions took about 8 minutes to build. Extrapolated, 10k revisions
  means about 2.3 s per create and about 3 hours to build; 50k means about 11 s per create and days to build.
- **Listing when the state matches no revision** walks that file's own revision trees. It is linear in that file's
  revisions: 195 ms at 2,000 revisions on one file, about 3 ms when spread.
- **Listing when the latest revision matches, preview (oldest or newest) and restore** stay flat at a few ms, apart
  from restore's tree-size cost. The Postgres projection is not a bottleneck.
- **First last-edit lookup after restart:** 218 ms on one file (about 4.1k commits) and 672 ms spread (about 5k commits
  touching 1,000 files).
- **Packing helps creation.** In the year scenario it roughly halved `revision.create`, from 205 ms to 111 ms at about
  440 tags, because packed refs and objects are cheaper to read than loose ones.

## 4. Storage growth (`storage-growth`)

One file is churned per kind. The deflate ratio of the generated content is measured, so "incompressible" is shown
rather than assumed. Packing means a manual JGit gc, run as a diagnostic: the prototype has no production maintenance.

| Kind | Saves | Save median | Growth per save (loose) | `.git` before packing | After packing | gc time |
| --- | --- | --- | --- | --- | --- | --- |
| Small text, 4 KiB, two-line diff (deflate 4.0×) | 20,000 | 4.9 ms | 1.6 KB | 32.9 MB (60k loose objects) | 13.3 MB | 22 s |
| Medium text, 1 MiB, two-line diff (deflate 6.1×) | 2,000 | 58.6 ms | 172 KB | 344 MB | 1.6 MB | 16 s |
| Binary, 1 MiB, full replacement (deflate 1.0×) | 1,000 | 48.2 ms | 1.0 MiB | 1.05 GB | 1.05 GB | 158 s |
| Binary, 10 MiB, full replacement (deflate 1.0×) | 200 | 416 ms | 10.0 MiB | 2.10 GB | 2.10 GB | 281 s |

Save latency stayed flat as each history grew. Answers to the two storage questions in the brief:

- **What do 10k saves of a 10 MiB changing binary do to storage?** About **105 GB**. Growth measured 10.49 MB per
  save, exactly linear, and packing recovers nothing. This case was not run to 10k; see "What could not reasonably run".
- **Do 50k ordinary text saves remain tiny after packing?** Mostly. Small text shrinks about 2.5× when packed (20k
  saves: 33 MB to 13 MB), so 50k saves would be about 80 MB loose and about 33 MB packed. Medium text with small diffs
  packs about 220×. Unpacked, 50k small saves left 151k loose objects (history-depth).

## 5. Concurrency (`concurrency`, `independent-workspaces`)

Each writer does 200 operations. "Distinct files": each writer saves its own file unconditionally. "If-Match": every
writer reads one shared file, then saves it with the token it read.

| Writers | Distinct: saves/s | Distinct: median latency | If-Match: acknowledged / conflicts | If-Match: acknowledged/s |
| --- | --- | --- | --- | --- |
| 1 | 122 | 6.7 ms | 200 / 0 | 157 |
| 4 | 155 | 24.8 ms | 201 / 599 | 59 |
| 10 | 144 | 65.4 ms | 200 / 1,800 | 27 |
| 20 | 124 | 157 ms | 200 / 3,800 | 13 |

| Independent workspaces (1 writer each) | Aggregate saves/s | Median latency |
| --- | --- | --- |
| 1 | 159 | 6.1 ms |
| 4 | 293 | 12.9 ms |
| 10 | 315 | 29.6 ms |
| 20 | 327 | 58.9 ms |

- **A single workspace serializes, as designed.** Throughput stays at about 120-155 saves/s whatever the writer count;
  the extra latency is queueing.
- **If-Match contention stays correct.** Exactly one save wins per round. Every acknowledged save is one link of a
  single history chain ending at the current state, and the current bytes are the last acknowledged save: no lost or
  phantom saves.
- **Independent workspaces hit a shared ceiling.** They scale about 2×, then plateau at about 300-330 saves/s from 4 to
  20 workspaces. So beyond per-workspace serialization there is a process- or machine-wide limit (disk, CPU or shared
  JGit state). It is not diagnosed here.

## 6. Remote round trip (`remote`)

An origin workspace grows: 50 files, with a revision every 10 saves. At each checkpoint:

1. the origin publishes;
2. a fresh clone is made;
3. a long-lived follower workspace syncs;
4. the follower publishes 5 new files back;
5. the origin integrates them, which is a merge.

| Origin saves (revisions) | Publish | Publish, up to date | Fresh clone | Follower incremental sync | Sync, up to date | Merge follower's work |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000 (100) | 877 ms | about 60 ms | 270 ms | (first clone) | about 17 ms | 149 ms |
| 10,000 (1,000) | 7,716 ms | 59 ms | 1,802 ms | 1,638 ms | 17 ms | 1,509 ms |

- **Clones arrive packed.** The 10k-save clone's `.git` is 6.1 MB, against 40.7 MB, mostly loose, at the origin.
- **Sync and merge cost grows with history.** Incremental sync and merge get slower with total history even though
  each delta is only a handful of commits. This was not broken down further.
- **JGit runs an unmanaged background gc.** During the remote scenario JGit started an automatic gc on its own worker
  thread, outside the workspace lock. It was presumably triggered by fetch/integrate under JGit's default `gc.auto`
  settings. The prototype therefore packs incidentally, but only in workspaces that sync with a remote. Production
  needs a deliberate choice: disable it and run explicit maintenance, or keep it and show it is safe alongside
  concurrent saves. It surfaced because it was still running when the harness deleted its data; the harness cleanup is
  now best effort.

## 7. Year-equivalent workspace (`year`)

The scale defaults:

- 3,000 initial files, 50,000 saves and 5,000 revisions;
- 30 hot files take 50% of saves and 70% of revisions;
- mostly small text, plus 2% medium text (64 KiB-1 MiB) and 0.3% 1 MiB binary files;
- some moves, deletes and creates;
- a restart, probe and remote sync every 10k saves.

**Neither variant can reach 50k saves in reasonable time on this backend**, because of finding 1: once the workspace
holds its files, each save costs 0.6-1.5 s. Both runs were budget-limited on purpose, and they report the state they
reached.

### Text only (`year.mediumShare=0 year.binaryShare=0`), 30 min budget

Reached: 3,010 files, 4,309 saves (3,000 of them creating the initial files), 430 revisions, 3 moves, 2 deletes, and
14 MB of content. Every check passed: all files, all revision lists, sampled revision content, the restart, the
follower sync, the fresh clone, and the workspace after packing.

| Operation (final state; the heaviest file has 17 revisions) | Median |
| --- | --- |
| Save existing / new file | 640 / 644 ms (flat at about 620 ms for the whole build) |
| Restore old revision | 622 ms |
| `revision.create` / rebuild | 205 / 197 ms |
| List revisions (matching / no match) | 2.7 / 4.2 ms |
| Read; preview oldest | 0.1; 1.8 ms |
| First last-edit lookup after restart | 1,502 ms (0.4 ms warm) |
| Publish (first push of all history) | 5.4 s |
| Fresh clone | 4.1 s |
| Manual gc | 9.5 s: `.git` 19.0 MB to 7.8 MB, 25k loose objects to 1 pack; `revision.create` then 111 ms |

Extrapolating from the flat save cost, the full 50k-save year would take about 9 hours to build on this machine.

### Default mix (medium and binary files), 20 min budget

The run never finished creating its initial files. It reached 1,565 of 3,000 files, with 31 MB of content, in
20 minutes, so the mixed workload of saves and revisions never started. The time to create each new file rose from
24 ms to 1,442 ms as the medium files accumulated. That is finding 1 driven by bytes rather than file count. Every check
passed, including the restart, clone and packing.

| Operation (final state: 1,565 files, 31 MB) | Median |
| --- | --- |
| Save existing / new file | 1,471 / 1,487 ms |
| Restore old revision | 1,450 ms |
| `revision.create` / rebuild (few tags) | 35 / 38 ms |
| First last-edit lookup after restart | 1,097 ms |
| Publish / fresh clone | 3.2 s / 3.3 s |
| Manual gc | 3.5 s: `.git` 14.6 MB to 10.0 MB |

## What could not reasonably run, and why

| Case | Status | Why, and what we know instead |
| --- | --- | --- |
| 10k and 50k revisions (one file and spread) | Stopped at 2,000 | Revision creation is O(total tags), so building is O(N²): about 3 h to 10k, days to 50k. The line is clean from 100 to 2,000, which puts 10k at about 2.3 s per create. An earlier scale attempt reached about 5,350 revisions before it was stopped, consistent with the line. |
| Year-equivalent at 50k saves and 5k revisions | Budget-limited (above) | Saves cost 0.6-1.5 s at year-sized trees (finding 1): about 9 h text only, much longer with the default mix. |
| Remote at 50k saves | Dropped | The trend from 1k to 10k saves is roughly linear (publish about 0.8 ms per save), which projects about 40 s to publish and 9 s to clone at 50k. |
| History depth at 100k (optional) | Not run | At 50k, saves had only gone from 16 to 25 ms. The cold last-edit walk (12 s at 50k) would roughly double. |
| 10 MiB binary × 10k saves | 200 saves run | About 105 GB and about 70 min. Growth is exactly linear (10.49 MB per save). Runnable with `storage.kinds=binary-10MiB:binary:10485760:10000`. |
| Real process restart with a cold OS cache | Not modelled | Restart is in-process, so first-request costs that depend on OS caches are understated. |

## Observations for the productionization decisions

These are inferences from the numbers, not changes made here.

- **The per-mutation whole-tree cost should be addressed first.** It affects every write at realistic workspace sizes,
  and it is independent of the fileId, rename-lineage and projection questions. Making it proportional to what changed
  means deciding two things: how much of the "working tree always equals HEAD" invariant to verify on every mutation,
  and who may write workspace directories. (The action server mounts the same `workspace_file_store` volume.)
- **Revision allocation should not scan every tag.** The projection is already cheap; the cost is the authoritative tag
  scan and validation on every create. Listing a file whose state matches no revision also needs a per-file state
  index, if single files will accumulate thousands of revisions.
- **History-derived metadata needs persistence or incremental rebuild**, so restart cost does not grow with history.
- **Maintenance needs a policy.** Loose objects accumulate without bound, and JGit currently packs only incidentally,
  in the background, after remote operations.
- **Binary content needs a product decision**, such as size limits, history pruning or external storage. At about
  1× its size per save it dominates storage, and packing cannot help.
- **Nothing in the data bears on fileId versus Git rename detection.** The workloads observe revision lineage only
  through the API, so the same scenarios can compare the two.
